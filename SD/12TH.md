# Caching

Caching means storing frequently used data temporarily in a faster place so that we can get it quickly next time.

# Consistent Hashing

Consistent hashing is a technique used in distributed systems to distribute data across multiple servers while minimizing data movement when servers are added or removed.

Policies for caching

1-> Cache aside
2-> Read through
3-> Write through
4-> Write around
5-> Write back

# Cache aside
In Cache-Aside, the cache and database do NOT directly communicate with each other.

Cache-Aside is a caching strategy where the application itself manages the cache.

In simple words:

First check the cache → if data exists, use it → otherwise get it from the database and put it into the cache.

It is also called Lazy Loading.

Example:

Suppose you want user 101.

User
 ↓
Application
 ↓
Check Cache


Case 1: Cache Hit 

Application → Cache
                 ↓
             User 101 found
                 ↓
              Application
                 ↓
                User

The database is not contacted.

Case 2: Cache Miss 

Application → Cache
                 ↓
              Not found
                 ↓
             Database
                 ↓
             User 101
                 ↓
          Store in Cache
                 ↓
             Application
                 ↓
                User

# Read through

The application talks to the cache, and the cache talks to the database when the data is missing.

Application
     ↓
   Cache
     ↓
   Database
Cache hit
Application → Cache → Data 

Database is not contacted.

Cache miss
Application → Cache
                 ↓
              Not found
                 ↓
              Database
                 ↓
              Cache
                 ↓
            Application

So in read-through, unlike cache-aside:

Cache ↔ Database communication exists.

# Write around
Write-around is a caching strategy where data is written directly to the database, bypassing the cache.

Application
     ↓
   Database
     ↑
   Cache 

                        How it works

Suppose we add a new user:

Application
     ↓
Database → Save User 101

The cache is not updated.

Later, when the application requests User 101:

Application
     ↓
Cache →  Not found
     ↓
Database → User 101
     ↓
Cache → Store User 101

So the cache gets populated only when the data is actually read.

# Write through

Write-through caching means whenever the application writes/updates data, the data is written to both the cache and database before the write is considered complete.

Application
    ↓
  Cache
    ↓
Database
                 Example

                 Suppose we update User 101:

Application
    ↓
Cache → Update User 101
    ↓
Database → Update User 101

Now both contain the latest data


# Write back:

Instead of directly updating the database, the application updates the cache and puts a message into a queue.

User
 ↓
Application
 ↓
Cache
 ↓
Message Queue
 ↓
Database (later)



Example

Suppose the user changes their name:

User → Application
           ↓
        Cache
           ↓
      "Update User 101"
           ↓
      Message Queue
           ↓
       Database

The application doesn't wait for the database.

So:

Cache → Updated immediately 
Database → Updated later
